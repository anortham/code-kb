# code-kb v2.13.2

This patch stops `check_edit` and the Stop hook from reporting a symbol as
removed when the extractor, not the edit, lost it. It bundles julie-extract
3.12.0 and keeps SQLite schema 8 and the seven-tool MCP interface.

## Symbols lost to a parse error

julie 3.12.0 parses a Razor file with a `@* … *@` comment inside an `@if`,
`else`, or `@foreach` block as one syntax error from line 1 to the end of the
file ([julie-extractors #29](https://github.com/anortham/julie-extractors/issues/29)).
The Razor compiler accepts the comment, so the project builds, but the index
keeps only the component class and its directives. A 1,300-line component
dropped from 302 symbols to 10.

The edit check compares the base scan of a changed file with its working rows.
With the working rows almost empty, it reported every `@code` member as
removed, listed each markup use as a `proven` site, and the Stop hook blocked
the turn on members that still compiled. Each new edit made a new diff, so the
block came back.

- `check_edit` now reads the `error` rows that julie writes in
  `parse_diagnostics` for the working file. A missing base symbol, field, or
  variant whose name still stands inside such an error is left out of the
  changes.
- One cut per file says so, with the names in source order:
  ``Not compared: 153 symbols of `src/.../ThemeDesigner.razor` whose names
  stand in a parse error at lines 1-1355 that the extractor reports:
  `ColorGroup`, `ColorToken`, `FieldProblem`, …. When the file compiles, the
  extractor cannot read a construct in it.``
- The Stop hook prints nothing for such a file, since the cut is no site.
- A symbol whose name is gone from the file is still reported as removed, also
  in a file with a parse error.

The rule applies to every language: any extractor parse error that drops
symbols now produces the cut instead of false removals.

## Known gaps

- The Razor comment itself is a grammar defect in `tree-sitter-razor`; the
  fix is tracked in julie-extractors #29 and will ship with a later
  julie-extract pin. Until then such a file has no `@code` members in the
  index.
- A symbol that was removed from a file with a parse error is not listed when
  its name still appears inside the error, in a use, a comment, or a string.
  The cut names it; check it by hand.

The release dogfood round on Flask found no wrong answer. Its gaps:

- `blast_radius` and `get_symbol_context` find no test for a method that only
  the WSGI runtime reaches (`Flask.handle_user_exception`); they name the open
  end and say to run the full suite.
- `check_edit` lists the reads of a removed Python attribute and not its plain
  writes (`app.testing = False`), since such a write still runs. For a removed
  descriptor such as Flask's `ConfigAttribute` the write silently stops
  reaching the config.
- `check_edit` keeps 50 test commands, and `offset` cannot page past them.
- The related tests of `get_symbol_context` can list a test whose name only
  contains the target's name (`test_client_open_environ` for `_client`).
- A whole-file `blast_radius` follows calls, not an import that builds an
  application at import time (`tests/test_cli.py::test_cli_name`).
- The lookup row of an `add_url_rule` with no view function shows no target;
  `code-kb facts route` says `no view function`.
- `find_references` on a widely used class repeats its construction sites under
  `Constructions` and lists every text-only line number.
- `file_skeleton` on a folder counts an unsupported file without naming it.
- A call on a subscript result (`environ["key"](ctx)`) is not a callee.

## Upgrade

- Restart running MCP sessions after upgrading. No rescan is needed.
