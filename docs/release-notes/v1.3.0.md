# code-kb v1.3.0

## Highlights

`search_symbols` and `lookup_symbol` no longer return rows from test files by default. A path rule now decides what a test file is, so helpers, fixtures, constants, and imports inside a test file are hidden together with the test functions the extractor flags. Equal rerank scores break by whole-token name strength, so a name that holds the query word as a whole token outranks a name that only contains it. No schema change, no index migration, no change to any MCP tool schema.

## Search

- **Test-file rows are hidden by default.** `julie-extract` sets `is_test` only on callable symbols that carry a test marker, so a helper or a constant inside a test file stayed visible. `code-kb` now adds its own path rule beside the two flags: `is_test_path` in `crates/code-kb-core/src/queries.rs` and its SQL mirror `test_path_predicate`, which a unit test keeps rule for rule identical.
- **The rule.** Back slashes become forward slashes, and the path is split into the directory part and the file name. A directory rule matches when the directory part, framed by slashes, contains `/test/`, `/tests/`, or `/__tests__/`, so it matches at the repository root too. A file-name rule matches when the lowercased file name starts with `test_` and ends with `.py` or `.rb`; when it contains `_test.`, `.test.`, or `.spec.`; when it is exactly `test.rs` or `tests.rs`; or when the raw file name ends with `Tests.cs`.
- **Production files keep their rows.** A file-name rule never reads a directory name, so `src/protocol.spec.v1/parser.rs` and `pkg/test_support/runtime.py` stay visible. The `Tests.cs` rule is case-sensitive, so `Contests.cs` stays visible. The bare endings `test.rs`, `tests.rs`, and `test.go` are not rules, because they hid `likely_tests.rs`, `latest.rs`, and `latest.go`. The `test_` prefix rule applies to Python and Ruby only, because a Rust module such as `test_quality.rs` is production code. A unit test pins 44 paths to their expected result.
- **The filter is lifted the same way as before.** `is_test: true` on the MCP tools and `--include-tests` on the CLI show test functions, test containers, and rows from test files again.
- **The rule also corrects `blast_radius`.** Its likely-tests list already used `is_test_path`; the rule as it stood needed a slash before `tests/` and so matched 225 of the 384,268 symbols under a root `tests/` directory on the hermes-agent index.
- **Whole-token tie-break.** `name_hits` now returns a strength per query word: 3 for a token run equal to the word, 2 for a stem match, 1 for a substring match of three or more characters, 0 for none. The rerank sort gains one key after `score` and before BM25: the sum of those strengths, descending. No score changed; only rows that already tied move.
- **`name_strength` in explain.** `code-kb search --explain` prints the strength sum per row, and the JSON `explain` object carries `name_strength`. The MCP tool schema is unchanged and takes no `explain` parameter.

## Evaluation (`docs/plans/021-search-v1.3-ranking-test-files-and-body-vocabulary.md`, results section)

Measured against the v1.2.0 released binary on the same machine, as file@1 / file@3 / symbol@1 / symbol@3 / not admitted.

|---|---|---|---|
| regression (plan 019) | 26 | 25 / 26 / 22 / 26 / 0 | 25 / 26 / 22 / 25 / 0 |
| development | 89 | 69 / 83 / 61 / 81 / 1 | 70 / 84 / 61 / 80 / 1 |

- Eleven cases rank one to three places lower and every one of them stays admitted. Hiding test-file rows frees slots under the recall caps and removes rows from the sample that sets the word rarity weights, so a different production row wins a close partial-name contest. The plan rules on each of the eleven by name.
- **Sealed acceptance set** (`acceptance-2.json`, 40 README-phrased queries, run once): file@1 20 of 40, symbol@1 16 of 40, 8 of 40 not admitted. Per repository, as file@1 / file@3 / symbol@1 / symbol@3 / not admitted: code-kb 6 / 8 / 5 / 7 / 0, hermes-agent 4 / 7 / 4 / 6 / 2, julie 7 / 7 / 5 / 7 / 2, miller 3 / 6 / 2 / 4 / 4. The v1 acceptance set in v1.2.0 was 19 of 40 file@1 and 14 of 40 symbol@1.
- **The plan's symbol@1 target was not met.** `development-2.json` gained 2 cases against a target of 5, and every per-repository acceptance target was missed. The remaining misses are README wording that appears in no name, signature, or docstring, which lexical search does not bridge.
- **Body vocabulary was measured and not built.** For 63 development misses, a query word equals an identifier name inside the expected symbol in 6 cases, and every matched word is a common identifier: the three most frequent appear inside 234, 104, and 68 containing symbols. A body branch weights only rows no other branch reached, so it would have moved 0 of the 63. The `identifiers` table holds `member_access` and `type_usage` names only; the expected symbol's body text holds at least one query word for 60 of the 63 misses, so a body-token branch needs call and variable identifiers from the extractor first. Design 4b was not built.
- **Warm `code-kb search` p50** on the code-kb checkout: 19.6 ms, against 17.9 ms for the v1.2.0 binary in the same run. The difference is the eleven-clause path predicate. The plan's ceiling is 25 ms.
- **Live `serve` RSS** after 20 searches: 29.8 MiB, against 29.5 MiB for v1.2.0.

## Compatibility

- **No index migration and no schema change.** `symbols_fts`, `symbol_names_tri`, `skipped_files`, and their triggers are unchanged, and the `fts_rule` marker does not move. A v1.2.0 index is read as is.
- **No MCP schema change.** `search_symbols` and `lookup_symbol` keep exactly `query`, `path`, `kind`, `is_test`, and `limit`. Explain stays CLI-only.
- **`blast_radius` and `find_related_tests` keep their test rows.** `blast_radius` predicts likely tests from the same corrected path rule, so a root `tests/` directory is now found.
- **What changes for a caller:** a search that used to return a helper from a test file now returns production code instead. Pass `is_test: true` or `--include-tests` to get the old result set.
