# code-kb v1.2.0

## Highlights

`search_symbols` finds substrings inside identifiers (`sha256` finds `parseSha256Sidecar`) and ranks results with a deterministic Rust rerank instead of raw BM25. The index gains a second FTS5 table for that, migrated once at the first start, inside one transaction. `code-kb search --explain` shows why each row ranks where it does. SQLite and FTS5 only: no embeddings, no in-memory index, no daemon.

## Search Recall

- **Trigram name index:** a new FTS5 table `symbol_names_tri` (trigram tokenizer over `name` only, locals and parameters excluded) sits beside `symbols_fts`. The same plain-SQL triggers keep both tables in sync, inside `code-kb` and inside the `julie-extract` process that writes `symbols`.
- **Three recall branches, each with its own capacity:** the word branch (FTS5, up to 40-160 rows), the trigram name branch (up to 20-40 rows, admitted even when the word branch is full), and the exact-name branch (always admitted, case-insensitive, served by the trigram index instead of a table scan). Rows are merged by rowid.
- **Query words also split like identifiers** for the name branch, so `collapse_name` reaches `CollapseName`.

## Search Ranking

- **Deterministic rerank:** one score per row from a const weight table in `queries.rs`: whole-name match, all query words covered by the name, partial name coverage (token runs, substrings, Porter stems, so `sha 256`, `sha256`, and `validation` all cover their names), signature and docstring coverage at token boundaries, a small kind prior (definitions above members, imports last), a small demotion for `scripts`, `examples`, `benchmarks`, `fixtures`, and `vendor` paths unless the query names them, documentation rows last, and a test-intent boost only when tests are included. Coverage weights each query word by its rarity inside the word index's matched rows.
- **A strong name match always outranks a kind or path prior**, so a constant, property, or enum member that is the exact answer still wins.
- **Word BM25 is a tie-breaker only**, so a row that only the trigram branch reached (no BM25) is never sorted behind every word row.
- **`score` in results is the rerank score.** `code-kb search --explain` prints the breakdown per row and a header with the candidate count, the rerank time, and the word weights; JSON adds an `explain` object per result (with `bm25`) only with the flag. The MCP tool schema is unchanged. `--verbose` stays debug logging.
- **In-repo corpus gate:** `crates/code-kb-core/tests/search_corpus_test.rs` scans a synthetic Rust, TypeScript, Python, C#, Go, and Markdown corpus with the real extractor and asserts top-1 for exact names, camel and snake case, name substrings, digit runs, short tokens, Unicode names, stems, concept queries over short enum variants, the kind and path rules, and admission past the word-branch cap.

## Evaluation (`docs/plans/020-search-v1.2-recall-and-rerank.md`, results section)

- Plan 019 regression set (26 queries on the code-kb checkout): file@1 22 → 25, symbol@1 17 → 21. Two queries rank one place lower than in v1.1.4, both by design (an exact-name struct above the functions; `create_index` above `ensure_fts_index`).
- Development set (89 queries over four repositories): file@1 55 → 69, symbol@1 42 → 61.
- Sealed acceptance set (40 README-phrased queries, run once): file@1 19 of 40, symbol@1 14 of 40; below the plan's target on three of four repositories. Most misses are vocabulary gaps between README wording and code names, which lexical search does not bridge.
- Warm `code-kb search` median on the code-kb checkout: 24.3 ms (v1.1.4: 21.9 ms); the rerank itself takes 0.44 ms at 177 candidates. Live `serve` RSS is unchanged within noise (about 0.2 MB).

## Index Migration

Every existing index migrates once at the next start. Measured on a copy of each index:

| Index | Symbols | Size before | Migration | Size after | WAL peak | Peak RSS |
|---|---|---|---|---|---|---|
| code-kb | 6,998 | 21.7 MiB | 25-34 ms | unchanged (262 KB reused from free pages) | 766 KB | 7.9 MB |
| hermes-agent | 990,975 | 1.62 GiB | 3.9 s (tmpfs), 5.8 s (NVMe) | +31.4 MB (+1.8%) | 73.4 MiB | 9.5 MB |

- The migration runs in one `BEGIN IMMEDIATE` transaction; the `fts_rule` marker is written last, so an interrupted migration reruns. The readiness check covers the marker, both tables, and both `_docsize` shadow tables; a missing table is recreated.
- **Failures surface:** `scan_workspace` and the CLI return the error; the MCP server reports it on the first tool call as `Index preparation of '<root>' failed: ...` and retries on the next call; `search_symbols` and `lookup_symbol` refuse to answer from an index that is not ready.
- **A second process waits instead of failing:** the migration connection uses a 60 s busy timeout and re-checks readiness under the lock, so a CLI call during a server-side migration blocks briefly and then answers.
- Trigger overhead on writes: update and delete medians roughly double (0.02 ms → 0.05 ms), inserts +0.1-0.26 ms; every median stays under 0.5 ms.
