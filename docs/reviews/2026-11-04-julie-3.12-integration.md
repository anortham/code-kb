## PowerShell consumer defect

The new real-extraction fact test found an unexported module function labeled
`proven` with basis `import`. Direct inspection confirmed that 3.12 correctly
writes a `kind=export` row with `export_kind=function` for `Get-Public`, and no
export row for `Get-Internal`. The existing `load_scope` walk flattened imported
files without checking exports, and `loaded_definers` treated every top-level
function in those files as visible. The same issue crosses nested module
boundaries. The [PowerShell export contract](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/export-modulemember)
confirms that explicit export commands restrict module members.

Before the source fix, `powershell_exports_test` had five failing negative cases
(unlisted, empty, dynamic, variable-only and nested exports) and three passing
positive cases (default functions, explicit comma-list/export-all, and nested
re-export). The hypothesis is that checking the queried function's export
permission at each module import edge fixes the false proof while retaining
those positive cases. Cache keys must include the queried name; other languages
keep their existing file-scope walk. Missing export proof remains conservative.
The implemented walk now checks indexed export commands and function export rows
at each PowerShell module edge, with the queried name in the scope-cache key.
Default exports, exact function lists and `*` remain provable. Missing, dynamic,
variable-only or unsupported pattern evidence leaves the scope incomplete
rather than inventing a binding. The existing four-hop and 64-file limits remain.

## Retained upstream limitation

A separate 248-byte T-SQL producer probe under the public 3.12 binary returned
`status=ok` at references level. Its `@AreaCode` identifier on line 6, column 11,
in `SELECT @AreaCode = SUBSTRING(...)` is `kind=variable_ref` with
`metadata_json={"access":"read"}`. The `RETURN @AreaCode` occurrence on line 7,
column 11 has the same access. The assignment is a write, so the former tag is
incorrect. Code-kb currently preserves it. The final regression asserts the
corrected `SET` write/compound/read facts and routine bodies; it does not assert
SELECT-assignment write coverage. No consumer heuristic or unpublished producer
build replaces the required public pin. This producer defect requires an
upstream correction and is recorded in language support.

## TypeScript body-fact compatibility

The first final workspace run stopped at the existing
`a_typescript_override_of_an_abstract_or_interface_method_has_no_range`
regression: calls were wrongly excluded as taking 1–2 arguments. Separate public
3.11/3.12 scans confirmed identical abstract/interface signatures and owners, but
3.11 incorrectly assigned their parameter lists as bodies, while 3.12 correctly
clears those body spans. Previously that accidental cut made the header reader
return unknown. With corrected spans it inferred a range from declarations.

The hypothesis is to preserve the existing conservative rule explicitly in the
ancestor walk: a TypeScript/TSX ancestor method without an implementation body
makes the inherited range unknown. This does not discard concrete method or
standalone overload ranges and does not change other languages. The original
failing test remains unchanged; its focused rerun passed before the workspace rerun. A new TSX regression also
passes, covering both bodyless ancestor kinds and a concrete ancestor whose
1–2 argument range still excludes calls outside that range. The second workspace
command uses `--no-fail-fast` to collect any remaining failures across targets.
