# code-kb 2.0 live tool review

## Scope and method

The shipped `code-kb 2.0.0` binary and this session's MCP registration were exercised against `/home/murphy/source/code-kb` at `ce801e2` plus the local review fixes. MCP discovery exposed exactly ten read-only tools and no workspace parameter. The live session covered normal use, scoped queries, test visibility, symbol IDs, ambiguity, stale IDs after a native edit, missing paths and symbols, invalid inputs, and `limit=0`. CLI parity was checked on the same cases that exposed defects.

The performance table uses `scripts/benchmark_quality.py` with one discarded warm-up and 30 measured calls per tool against the shipped release binary. This is one local repository and one machine, not a cross-version comparison. Estimated tokens are answer size, not cumulative savings; each baseline is the size of the file or files an answer points into.

Reproduction command: `python -B scripts/benchmark_quality.py --binary target/release/code-kb --cwd /home/murphy/source/code-kb --iterations 30 --json-output /tmp/code-kb-v2-dogfood-benchmark-30.json`.

The benchmark's six targeted lookup, search, and impact checks ranked their expected target first. Fresh CLI query median was 15.55 ms. A fresh MCP handshake took 683 ms, and detection of a newly added source symbol took 262 ms. Skeletons saved 77.1–93.6% of the measured file tokens; three context slices saved 88.8–98.9%.

## Defects found and fixed locally

- `limit=0` made lookup, search, references, and facts claim that no matches existed. CLI and MCP text now say the zero limit hides results. JSON CLI still returns the requested empty arrays.
- The MCP schema called fact and impact limits "combined" even though each result section has its own cap. Both descriptions now state the per-section behavior.
- The benchmark used the removed `validate_syntax` symbol, so its MCP run failed and its search score was 5/6 for a nonexistent target. It now uses `sanitize_fts5_query` and measures all ten tools, including facts.

## Quality and efficiency observations

- A whole-file skeleton for the 6,297-line `queries.rs` costs about 15,796 tokens. It saves 80.2% against the raw file, but `lookup_symbol` and `get_symbol_context` give much smaller answers when the target is known. The Python skeleton also includes some extractor-produced multiline assignment and lambda fragments.
- `find_references` spends its default 20 rows on call sites, not unique callers. On `search_symbols`, those rows came from five test functions. `blast_radius` condensed the same area to five test targets. This is an output tradeoff; changing reference grouping would alter the call-site contract.
- A mixed query with a nonexistent term, `zzzxqv no such concept 98431`, returned weak partial matches through the search fallback. A single nonexistent identifier returned no matches. Suppressing partial matches would trade recall for precision, so this review did not alter ranking.
- File-level impact for `server.rs` initially predicted two stem-matched adversarial test files and missed `mcp_test.rs`; uncommitted-change impact did include `mcp_test.rs`.
- Fresh MCP RSS was 20.98 MB after initialization and 40.83 MB after the 30-call-per-tool workload. A separate 20-pass run rose to 37.18 MB and leveled off; 20 search-only calls rose from 20.68 to 38.90 MB. This does not show unbounded growth, but it exceeds the repo guideline's approximate 25 MB retained figure for this workload. No memory optimization was attempted without a before/after candidate.

## Follow-up: file-level test prediction

The `server.rs` miss came from matching only a source file's basename. A file under `src/<module>/` now also looks for tests named after that module. `blast-radius --file crates/code-kb-cli/src/mcp/server.rs` returns `mcp_test.rs` as a module-matched test; `scripts/benchmark_quality.py` still returns only its stem-matched test. A focused regression test failed before the change and passed after it; all 15 blast-radius integration tests pass.

The final Linux tree passed 396 Rust tests, workspace clippy, formatting, and diff checks.

For that same `server.rs` query, 30 warm fresh-CLI runs measured p95 29.55 ms before and 21.05 ms after, with peak exited-process RSS 32.88 and 32.77 MB. The after run was second, so these numbers show no observed regression rather than a causal speed gain. The answer grew from about 207 to 256 tokens to include the missing test.

## Claude CLI review before patch release

Claude CLI 2.1.280 completed a read-only review of `ce801e2..de7c9a7`. It found one medium issue: module names matched anywhere in a test path and could crowd out more specific file-stem matches. A regression fixture reproduced an unrelated `code-kb-cli` test ranking ahead of the target test at `limit=1`. The query now checks test basenames, skips universal module names, scans at most 200 module candidates, and orders all file-stem matches first. A second, low-severity finding noted that the ceiling and empty-result text still said "stem-matched"; both messages now cover name matching generally.

The new regression test and formatter assertion failed before their fixes and passed after. All 16 blast-radius integration tests and the formatter test pass, as do workspace clippy and formatting. The same `server.rs` fresh-CLI workload was measured across 30 warm calls: the old build's p95 was 49.61 ms; the candidate's settled warm p95 was 27.00 ms. The first candidate run had startup contention, so this is evidence of no sustained regression, not a claimed speed gain. Peak exited-process RSS was 33.49 MB before and 34.03 MB after.
