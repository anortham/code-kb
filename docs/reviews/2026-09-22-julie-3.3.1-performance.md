# julie-extract 3.3.1 performance audit

This audit compares the release baseline, code-kb `a36f2c5` bundled with
julie-extract 3.3.0, with main at `a656920` bundled with 3.3.1. The candidate
was built with the pinned extractor and the baseline was rebuilt from its
archived source at the matching revision. Binary and extractor SHA-256 values,
commands, host snapshots, and raw results are durably packaged outside this
repository at `~/.code-kb/perf-audits/2026-09-22-julie-3.3.1/`.

The broad comparison matrix describes the original `a656920` candidate with
the forced-header-refresh path. Final `1155ddf` replaces that path with the
normal content-aware scan and has focused header, Windows, Linux, and unchanged
read-path retests below. The broad query/extractor matrix remains attributable
to `a656920`; it must not be described as a fresh broad measurement of `1155ddf`.

## Result

The original 3.3.1 candidate has no material scan, database-size, retained-memory,
launcher, or mutable-search-quality increase in the measured workloads. The
final build removes its forced-header refresh regression while preserving Qt
property facts. A residual cost remains relative to the released but incorrect
single-file header update, which loses those facts. Kirigami MCP lookup retains
a +0.276 ms p95 movement with a nearly flat median; its cause is unestablished.

The targeted persistent-MCP tail retest cleared the initially noisy tails. The
mutable search replay completed 215 cases across three paired passes. Sealed
acceptance sets were not executed.

## Provenance and method

- Candidate: main `a656920418ec821f2804496a959f6e86890cee40`, code-kb 1.6.0,
  julie-extract 3.3.1.
- Baseline: `a36f2c5ff8818a7aaa777ced1a44f13af128abde`, code-kb 1.6.0,
  julie-extract 3.3.0.
- Both variants used fresh, isolated SQLite indexes at the `facts` level. Each
  matched workload discarded its warmup and alternated baseline/candidate runs.
- The fixed source workload was the tracked tree at `a656920`; local benchmark
  harness edits were excluded from the source snapshot.
- Runtime percentiles use the nearest-rank order statistic. The Qt runner uses
  its interpolated percentile estimator. Tables identify sample counts and do
  not compare percentiles across those measurement families as if the estimator
  were identical.

### Header refresh boundary

| Action | 3.3.0 p95 | 3.3.1 p95 | Correctness outcome |
|---|---:|---:|---|
| Kirigami, one `.h` edit | 41.06 ms | 2129.90 ms | candidate preserves facts; baseline loses 2 |
| Kirigami, five offline `.h` edits | 122.58 ms | 2165.18 ms | candidate preserves facts; baseline loses 5 |
| Plasma, one `.h` edit | 173.65 ms | 15413.75 ms | candidate preserves facts; baseline loses 5 |
| Plasma, five offline `.h` edits | 285.95 ms | 15367.78 ms | candidate preserves facts; baseline loses 5 |

Those rows describe the original forced-refresh candidate only. The final
implementation uses the normal content-aware workspace scan, which changes only
the affected rows. With one discarded warm-up and three retained samples, the
identical append-newline workload p95 is now 61.53/82.34 ms for Kirigami
one/five-header batches and 375.39/356.69 ms for Plasma: 97.1%/96.2% and
97.6%/97.7% faster than the forced candidate. All property-fact deltas are zero.

A separate same-size, restored-mtime test also passes all per-header language,
hash, property, aggregate-row, and control-row assertions: p95 is 59.61/76.39
ms for Kirigami and 364.04/388.94 ms for Plasma. The normal scan is therefore
the safe replacement for the forced path. It remains slower than the released
baseline's incorrect single-file update (Plasma 173.65 to 375.39 ms single and
285.95 to 356.69 ms batch), because that fast path loses Qt property facts.

## Search-quality audit

The mutable search replay covers `regression.json` (26 cases), `development.json`
(89), `development-2.json` (60), and `development-3.json` (40) on frozen tracked
snapshots: 215 cases total. It runs each binary against its own matching index.
This report records aggregate rank counts and percentiles only; raw result
files remain outside the repository because they contain protected query and
expected-answer data.

`acceptance.json`, `acceptance-2.json`, and `acceptance-3.json` remain sealed
historical evidence and were not rerun.

Three alternating paired passes produced 645 observations per binary and 645
paired cases. File@1/file@3/symbol@1/symbol@3/not-admitted counts are identical:
504/579/450/540/27. The 78 regression-set observations per binary are likewise
identical at 75/78/69/75/0. No file-rank or symbol-rank regression occurred.

## Saved benchmark families and limits

- `scripts/benchmark_quality.py`: fresh CLI/token compression, persistent MCP,
  reconciliation, and synthetic large-corpus measurements. Its report writer
  and MCP response validation were corrected before this audit; prior default
  JSON reports and fallback-based reconciliation measurements are not trusted.
- `~/.code-kb/search-eval`: durable rank and query-latency baselines from 1.1.4
  through 1.4.0, plus the current mutable replay. Historical sealed acceptance
  summaries are retained without rerunning their workloads.
- README's four real Qt/QML corpus pins are the relevant extraction-scale gate.
- The upstream Julie corpus report is provider-only evidence on partially
  different revisions; it is not substituted for code-kb measurements.
- Plugin launcher measurements include both POSIX `execve` and fallback process
  tree paths. The fallback has a much larger retained footprint by design.

## Evidence retention

The durable audit directory is
`~/.code-kb/perf-audits/2026-09-22-julie-3.3.1/`. It contains binary/extractor
manifests and hashes, build logs, raw runtime reports, raw Qt/QML reports,
mutable-search results and drivers, Windows logs, and `SHA256SUMS`. It excludes
corpus working copies, SQLite databases, sealed evaluation inputs/results, and
the Windows source clone. This report contains no search query or expected-answer
text.

## Final-build verification

The header-refresh implementation was committed as
`1155ddfe9e36497aeecd67177f70fff1b7454cc8`. Its Windows NTFS scope passed 33
targeted tests with julie-extract 3.3.1. Linux passed 416 workspace tests,
clippy, format, four benchmark-harness tests, and the diff check. The final
release build uses the pinned extractor and is separately manifested with its
binary and extractor hashes.
