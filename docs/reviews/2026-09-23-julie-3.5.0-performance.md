# julie-extract 3.5.0 performance check

## Result

The new extractor returns the expected Go manifest rows and keeps all six benchmark searches at rank 1. Search latency and retained memory increased on the measured code-kb snapshot. Fresh scans also take longer on the larger upstream snapshot, which produces more rows. These costs are measured release tradeoffs.

## Method

- Baseline: code-kb 2.0.1 with julie-extract 3.3.1. Candidate: code-kb 2.0.2 with julie-extract 3.5.0. Each run set `JULIE_EXTRACT_BIN` to its matching binary; SQLite artifact metadata confirmed the extractor version.
- The code-kb source was archived at `0fb2625` into separate clean directories. Benchmark reports were written outside those directories. Both indexes used the `facts` extraction level.
- The larger corpus was an archive of julie-extractors `47be8168`, scanned with each extractor directly. Its 1 GB artifacts and temporary spool files lived on the regular filesystem. Four alternating fresh scans per version discarded round 0.
- MCP timings used three alternating sessions per version, two warm-up calls per session, then 100 calls per session and tool. Percentiles use nearest rank. Memory used three new sessions per version after 20 search calls.
- Raw reports, timing samples, scan samples, binary hashes, and logs are at `~/.code-kb/perf-audits/2026-09-23-julie-3.5.0/`.

## Measurements

| Workload | 3.3.1 | 3.5.0 |
|---|---:|---:|
| Upstream source fresh scan, warm median (3 each) | 14.95 s | 17.86 s |
| Upstream source fresh scan, warm p95 | 17.44 s | 18.01 s |
| Upstream source symbols | 685,663 | 728,606 |
| Upstream source artifact | 1.071 GB | 1.254 GB |
| code-kb snapshot symbols | 8,598 | 8,945 |
| code-kb snapshot structural facts | 2,461 | 2,723 |
| code-kb snapshot artifact | 26.8 MB | 31.4 MB |
| MCP search p50 / p95 (300 calls each) | 8.30 / 8.80 ms | 10.11 / 10.54 ms |
| MCP references p95 (300 calls each) | 1.90 ms | 2.03 ms |
| Live MCP RSS median (3 sessions each) | 14.39 MB | 14.76 MB |
| Live MCP PSS median (3 sessions each) | 9.29 MB | 12.22 MB |
| Live MCP anonymous memory median | 6.51 MB | 6.77 MB |
| Synthetic 500-file scan, one sample | 76.33 ms | 78.87 ms |

The three warm upstream scan samples were 14.924, 14.950, and 17.441 seconds for 3.3.1, and 17.801, 17.862, and 18.014 seconds for 3.5.0. Median scan time rose 19.5%; p95 rose 3.3% because one baseline sample was slow. The extractor wrote 6.3% more symbols and the artifact grew 17.1%. No scan reported a failed file on the regular filesystem.

Search p95 rose 19.7%, or 1.74 ms per call, on the fixed code-kb snapshot. The candidate reranked fewer candidates and its one sampled rerank timer was lower, so the measured increase is before reranking; this check did not profile SQLite in enough detail to name a narrower cause. The candidate's 14.76 MB live RSS remains below the project's roughly 25 MB retained-memory reference.

## Compatibility checks

- A fresh Go sample indexed `go.mod` as `gomod` and `go.sum` as `gosum`. `code-kb facts manifest.dependency.v1` and `code-kb facts gosum.checksum.v1` each returned the expected row.
- Opening a 3.3.1 sample artifact with the 3.5.0 candidate rebuilt it to the new extractor version.
- A direct 3.5.0 single-file `.h` update still reclassified a Qt C++ header as C and lost its property fact. The existing content-aware header scan remains necessary.
- QML reference tests exposed a new `id` type fact that could override a same-named local receiver. The shared resolver now rejects that false match and keeps unshadowed `id` calls.
- The quality benchmark's six searches kept their top result in both versions. The synthetic scan is a smoke check with one sample, so it is not evidence of a stable speed change.

Two preliminary code-kb benchmark runs were discarded: the running binary selected another installed extractor, and the report file was written inside the measured source directory. The final runs above used explicit extractor paths, verified artifact metadata, and kept reports outside the corpus.
