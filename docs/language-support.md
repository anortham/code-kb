# Language support and observed fixture coverage

`code-kb` accepts every language reported by its pinned `julie-extract`. The
language conformance test reads the installed `julie-extract languages --json`
report at runtime, then checks that both the fixture directory set and
`evals/languages/fixtures.json` match it. The current pinned report is Julie
3.10.0 with 42 language IDs.

Fixture sources live under `evals/languages/tests/<language>/` so they are
excluded from this repository's default searches. Paths in the table and
manifest's `file` field are copied to production-like paths inside a temporary
project before scanning.

Julie capability flags and code-kb behavior are separate evidence. The
capability column records only the booleans in Julie's `actual_capabilities`
report. The observed column lists operations the real-extractor fixture runs
through code-kb's shared core APIs. A listed operation proves the fixture case
works; it does not establish complete grammar or project-wide language support.

The operation codes describe fixture assertions:

- `L`: exact name lookup through `lookup_symbols_op`; `L∅` is a path-scoped empty lookup for the intentional no-symbol case.
- `O`: `file_skeleton_op` includes the expected symbol or says that the file has no symbols.
- `B`: `get_symbol_body_op` returns a non-empty body and any configured body marker.
- `C`: `get_context_slice_op` returns the selected symbol and a non-empty target body.
- `R`: `reference_report` includes the fixture caller or reference source.
- `I`: `blast_radius_op` includes the fixture caller or reference source.
- `U`: `update_file` refreshes the changed fixture; every symbol name is replaced and the no-symbol fixture stays empty.
- `E`: `edit_check_op` reports the configured definition change and caller evidence. Separate-line callers must be proven or likely; a caller on the same physical line as the edit may be reported as `in_diff`. CSS separately checks custom-property and selector changes.

## Capability and fixture boundaries

- `S`, `I`, `P`, `R`, and `T` in the table mean Julie reported `symbols`, `identifiers`, `pending_relationships`, `relationships`, and `types`, respectively. `—` means all five flags were false. These report values are not inferred from the core behavior checks.
- Every symbol-bearing fixture checks exact lookup, skeleton visibility, body retrieval, context retrieval, and an incremental refresh. Caller fixtures additionally check caller references, impact, and edit detection. The structural fixtures intentionally have no caller or cross-symbol reference to exercise; those specific checks are semantic N/A for the fixture, not claims that the language can never express references.
- The XML fixture uses a valid MSBuild project file so the extractor has script symbols and a same-file call to navigate. It does not stand in for every XML vocabulary.
- The XML edit fixture is one physical line, so the line-based diff reports its `caller_xml` site as `in_diff`; this is expected for a call on the changed line. Separate-line callers in the other fixtures must still be proven or likely.
- CSS uses a selector, a public custom property, a `var()` reference, and explicit `@function` custom functions. Julie writes each `@function --name(...)` as a `function` row named by its decoded name (`--escaped\ name_css` is `--escaped name_css`; the signature and the skeleton keep the written spelling), and each call as a `call` identifier with that decoded name and `arg_count`. ASCII, Unicode, and escaped declarations are checked through lookup, skeleton, body, and context, and their calls across references, context, and impact. [`result-call.css`](../evals/languages/tests/css/result-call.css) checks a `result:` call whose name extends a shorter function's name (`--foo名` and `--foo`), and [`other-stylesheet.css`](../evals/languages/tests/css/other-stylesheet.css) checks a call of a function that another stylesheet declares. The fixture reports CSS parse diagnostics while still extracting the selected symbols; this is limited syntax coverage. The fixture's ordinary declarations are not expanded into standalone symbols.
- Erlang's exported function name occurs in both the export attribute and declaration. Its refresh changes both declaration-bearing occurrences while leaving the caller's old call in place so edit-check evidence remains meaningful.
- `gosum` is an intentional no-symbol fixture. Its checksum is changed and rescanned; no symbol, body, or caller is expected.

### CSS custom functions

Custom functions are global across the stylesheets that a page loads. Julie
writes a `calls` relationship for a call whose file declares the function, and a
pending call for one whose file does not. code-kb reads these facts as they are:

- A call of a function in its own file is `proven` (`same file`).
- A call of a function that another stylesheet declares is `likely` (`name
  only`) when one stylesheet declares it, and `unresolved` when two or more do,
  because the order in which the page loads them decides. A CSS custom function
  is the one CSS row that counts as another definition of a site.
- Names compare after julie decodes their escapes, and a name with U+2000 (EN
  QUAD) is kept whole. The text scan of the callers report looks for the decoded
  name, so it does not count a line that writes the name with an escape.
- A call shows its `arg_count`, but no count excludes a site: julie writes no
  parameter rows for a custom function.
- Julie limits: an `@function` with a `returns` clause has no symbol, and a call
  outside every rule has no caller, so it is no site.

Examples: `a_css_call_reaches_a_function_declared_in_another_stylesheet`,
`a_css_call_that_two_other_stylesheets_can_satisfy_is_unresolved`,
`a_result_call_with_a_longer_unicode_name_reaches_only_that_function`, and
`an_updated_stylesheet_moves_a_call_to_the_renamed_function` in
[`css_custom_function_test.rs`](../crates/code-kb-core/tests/css_custom_function_test.rs),
and `css_custom_function_calls_reach_their_functions_in_this_and_other_stylesheets`
in [`language_conformance_test.rs`](../crates/code-kb-core/tests/language_conformance_test.rs).

## Cross-language consumers and test scope

The controlled pilot exposed consumer errors that the language inventory alone did not catch. Same-named Go/C#/TypeScript/Java/Rust methods could contaminate impact and context output. The shared call policy now retains same-language candidates for every indexed ID and preserves the existing JS, JVM, .NET, and C-family interoperation groups. Name-only identifiers and pending type uses keep their narrower rules, including directional QML-to-C++ matching. Compatibility permits a candidate; owner, receiver, import, or scope evidence must still establish the edge.

`cross_language_graph_test.rs` uses real extraction for the reported collisions, file-seeded impact, context dependencies/tests, and fallback behavior. Some JVM/.NET/C-family policy controls remap an existing extracted call row inside a rolled-back transaction because the fixture call was absent from extraction. These consumer controls do not establish end-to-end extractor interoperation coverage.

Broader runner discovery currently recognizes compatible Cargo, Go module, npm test-script (not the `npm init` placeholder that prints `no test specified` and exits 1), Maven/Gradle (a Gradle build runs through the nearest `gradlew`, or `gradlew.bat` on Windows, at or above its folder: `cd app && ../gradlew test`; a project of a multi-project build runs its own task from the settings folder, `./gradlew :app:test`, and has no command when the settings file cannot name it with certainty), pytest, and .NET test configurations. It supports the relevant script/JVM/.NET file variants, requires Rust package evidence for scoped files, and stops at an unconfigured nearer package. Simultaneous runner families or build tools, missing configuration, unknown extensions, and conflicting reported scopes use the manual-suite fallback. sbt (`sbt test`) joins the JVM family; other runner ecosystems have no broader command yet, so their answers say `Run the full test suite.`

Targeted test commands (`test_commands.rs`, rules in [`reach-sections.md`](reach-sections.md)) cover Python, Rust, Go, JavaScript, TypeScript, TSX, JSX, Java, Kotlin (JUnit methods, and Kotest labels through Gradle), Scala (JUnit, ScalaTest, and MUnit through sbt), with a Gradle project of a multi-project build run by its own task (`./gradlew :app:test --tests 'Class.name'`; Groovy and Kotlin settings files; Groovy test files have no extractor), C#, F#, VB.NET, Ruby (RSpec, Rails, Rake `TestTask`, test-unit), Swift, Dart (`dart test`, `flutter test`), C++ (GoogleTest through a configured CTest build), C (Unity through Ceedling; CMocka, Check, and other C tests through the CTest test of their executable), Zig (`zig test`, or `zig build test` with a `test-filter` option), QML (Qt Quick Test through `qmltestrunner`), PHP (PHPUnit), Elixir (`mix test`), Erlang (rebar3 EUnit and Common Test), Lua (busted), R (testthat), PowerShell (Pester), Bash (bats), and GDScript (GUT, and gdUnit4 by suite).
