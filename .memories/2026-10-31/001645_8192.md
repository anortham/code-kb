## Fixed 5-minute blast_radius and 44 s callee calls

After v2.11.1 the size probe showed `blast_radius --file include/nlohmann/json.hpp` at 381 s, Newtonsoft LinqBridge.cs at 284 s, gson bind folder at 99 s, aspnetcore ControllerBase at 98 s, and aspnetcore `ExecuteAsync` callees 44 s / context 27 s.

- **Cause 1:** the typed receiver-chain term of `pending_target_predicate` inlined the 65 KB owner SQL; SQLite re-ran it per read of the `receiver_owners` CTE, per (pending call, target) pair.
- **Fix 1:** `receiver_chain_owner_map` computes owners once (per walk level, per callee source) and binds a JSON map; `bound_receiver_chain_owner_sql(param)` reads it. Used in `CallerWalk::extend`/`open_ends`, `callee_page_cte`, `find_callee_signatures`.
- **Cause 2:** with a NULL owner the status query still ran (30 KB). A NULL owner can only give status NULL/0, so a bound owner adds `owner IS NOT NULL AND` first.
- **Cause 3:** the `closer` top-level check scanned all same-name defs (nlohmann has 254 `json` aliases) with rank CASE per row; rewritten as `CASE target_rank WHEN 2 THEN 1 WHEN 1 THEN same-file check ELSE same-folder check`, ~40% faster on that branch.

## Results (MCP, same workload)
json.hpp 334 s → 17 s; LinqBridge 284 → 6.5; gson bind 101 → 16; ControllerBase 83 → 4.2; TelegramAdapter 30 → 7.8; ExecuteAsync callees 44 → 3.2; context 27 → 3.1. Answers identical except time-limited counts. Reach gate tables identical to v2.11.1; 2335 tests pass.

Not changed: `find_related_tests`, `find_direct_references`, `describe_callee_targets` still inline the owner (not measured slow).
