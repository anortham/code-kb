## Fixed: code-kb ran a foreign repo's julie-extract and deleted its index

**WHAT:** `crates/code-kb-core/src/sync.rs`
- `julie_extract_candidates` no longer walks the current directory for `.tools/julie-extract`. It walks up from the executable's directory instead, so a source build still finds the checkout's `.tools` above `target/`.
- `ensure_index_matches_extractor` keeps an index when the artifact metadata or any `extraction_revisions` row was written by a newer extractor than the one in use (`newest_writer_version`, `version_is_older`).
- New `rebuild_index` scans into `artifact.db.rebuild`, checkpoints it, and renames it over the index only after success.

**WHY:** On 2026-09-23 a code-kb CLI call run from inside `~/source/miller` picked Miller's vendored extractor 2.42.0 (no candidate matched the 3.3.1 pin of the stale local 2.0.1 build). The version guard deleted Miller's index before the rebuild, and the rebuild failed (`--level facts` unknown). Plan 017 had already asked to drop the upward walk; only the compare half had landed. It was also a security issue: running code-kb in a repo executed that repo's binary.

**HOW:** TDD. Four red tests first: `test_cli_never_runs_the_julie_extract_of_the_directory_it_starts_in` (cli_test, unix; had to use the system temp dir because `safe_tempdir` is under `target/`, where the walk finds the pinned build), plus three in freshness_test (newer metadata, newer file rows, failed rebuild keeps old index).

**IMPACT:** 409 Linux tests, fmt, clippy, and 17 plugin tests pass. Miller's index was restored with 3.5.0. Docs: CLAUDE.md/AGENTS.md section 7, release notes v2.0.2.
