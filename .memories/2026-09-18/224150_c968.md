## Cross-language check: chained call `Outer.Inner.chain()` receiver loss (2026-09-18)

**WHAT:** Scanned one sample per language with julie-extract 3.1.0 (scratchpad `langs/`), then ran end-to-end `code-kb refs chain` repros with a nested target in one file and a chained call in another (scratchpad `e2e/`).

**Findings by shape of the pending relationship for a three-part chain:**
- Receiver dropped entirely (same as the C# report): C#, Java, Kotlin, Go, PowerShell (PowerShell loses it on two-part `[Two]::Part()` too). code-kb finds nothing for C#/Java/Kotlin. Go still matches by accident because Go methods have no parent symbol, so the bare-name branch of `pending_target_predicate` accepts it.
- No pending row at all: C++ (`Outer::Inner::chain()` emits nothing; `Two::part()` loses its receiver), Zig, JavaScript/TypeScript (no pending row and no call identifier; only a member_access for `Inner`). code-kb finds nothing.
- Compound receiver string ("Outer.Inner", "Outer::Inner", "Outer$Inner"): Python, Swift, Dart, Lua, GDScript, C, PHP, Ruby, R. code-kb compares the receiver to the parent symbol name, so it never matches. Verified 0 callers for Python and Swift. Ruby is rescued only by the name-only member_access identifier fallback.
- Correct: Scala and VB.NET (receiver `Inner`, namespace `[Outer]`), Rust/Elixir/F#/Erlang (namespace path). Verified callers found for Scala and Rust.

**Also:** the call *identifier* path already records `{"receiver":"Inner","receiver_qualifier":"Outer"}` correctly in almost every language. Only the relationship-target path is broken. That is the reference implementation for the fix.

**IMPACT:** the user report is one instance of a family-wide gap. Fix plan: julie flattens the member-access chain into namespace + receiver for every relationship extractor (JS/TS/C++/Zig also need to emit the row); code-kb accepts a compound receiver by its last segment and filters the identifier fallback by receiver when the target is nested.
