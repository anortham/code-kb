## Output budget for large tool replies (branch fix/output-budget, uncommitted)

- **WHAT:** Added `OUTPUT_BUDGET_CHARS` (32,000 chars, about 8K tokens) in `formatters.rs`. File skeletons render rows breadth-first until the budget, collapse containers to `{ /* N rows hidden: Lx-Ly */ }`, and fold the rest into `/* N more rows: Lx-Ly */`. `fit_body_to_budget` in `ops.rs` replaces a large container body with its member skeleton, or cuts other source with a `Read lines A-B` pointer (text only; CLI `--json` keeps the full body). Folder outlines step down names per file (5,3,2,1,0), then one level, then cut lines.
- **WHY:** A 9-repo MCP size probe (273 calls) found replies up to 438 KB: lock files, JSON data, Markdown, big C++ headers, class bodies in `get_symbol_context` (114 KB), and wide folder outlines (67 KB).
- **RESULT:** No reply over 34.5K chars after the fix; 1.59 MB -> 0.34 MB on the 12 worst calls.
- **Probe:** scratchpad scripts `mcp_sizes.py` and `make_cases.py` drive `code-kb serve` over stdio.
- **Separate latency defects (not fixed):** `blast_radius` on a file or folder took 334 s (nlohmann-json `include/nlohmann/json.hpp`), 284 s (Newtonsoft `Utilities/LinqBridge.cs`), 101 s (gson `internal/bind`); `blast_radius ControllerBase` (aspnetcore) 83 s; callees of aspnetcore `ExecuteAsync` in `ErrorPage.Designer.cs` 44 s.
- **Wording gap:** the ambiguity error says "found 25 matching candidates" when the SQL cap of 25 hides more.
