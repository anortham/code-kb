## notify 9.0.0-rc.7 upgrade on ckb/notify-9

- **What:** notify `=9.0.0-rc.7`, notify-types 2.2.0. Debouncer copy re-vendored from notify-rs/notify 7d09a58 (debouncer-full 0.8.0-rc.2 + unreleased fixes), keeping code-kb's BTreeMap roots and WatchNotFound unwatch patch. std HashMap instead of rustc-hash.
- **Windows:** notify 9 reports RDCW start failure from `watch()`, rearm failure as an error event (then drops the watch), and overflow (`ERROR_NOTIFY_ENUM_DIR` or 0 bytes) as a pathless rescan event. An unknown completion error still only logs and drops the watch. code-kb now (1) re-watches the recursive root when `watch_again` is set after any error or rescan, (2) checks `watched_paths()` every 1 s and records a failure plus reconcile when the root watch is gone. A failed re-watch is a registration failure (unhealthy until it recovers).
- **macOS decision:** recursive root watch on macOS too (`RECURSIVE_ROOT_WATCH = cfg!(any(windows, macos))`), NoCache everywhere. Reason: notify rc.5 refuses FSEvents streams beyond RLIMIT_NOFILE/12 paths (`MaxFilesWatch`); every nonrecursive watch is its own stream path, so per-folder registration fails at ~21 folders with soft limit 256. FSEvents is recursive per path anyway. Not verified on a Mac here; needs macOS CI.
- **Memory:** notify 9 alone adds ~3-4 MiB retained RSS on Linux (base c2775f9 26 MiB after calls, notify-9-only build 29-30, full change 28-30). Code changes add nothing measurable.
- **Tests:** 4 new watcher unit tests force a recursive root on Linux and inject a native error, a rescan, a dropped watch, and a failing re-watch; all 4 fail without the fix.
