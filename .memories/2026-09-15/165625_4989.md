## Plan 017: code-kb + julie-extract product cohesion assessment (read-only)

**WHAT:** Wrote `docs/plans/017-product-cohesion-assessment.md`. No code changed in either repo.

**WHY:** User asked whether code-kb and julie-extract, seen as one product, have gaps.

**HOW:** Code reading plus live runs on `~/source/miller` (2,471 files, 240k symbols) and fresh scans into the scratchpad.

**Findings, ranked:**
1. Defect (confirmed): runtime discovery walks upward for `.tools/julie-extract` before PATH and found miller's vendored 2.42.0. `ensure_index_matches_pin` compares recorded version to the pin, not to the found binary. Every CLI call and server start on miller rebuilt the 1.3 GB index (22 s, 2.1 GB RSS). Fix: compare to the found binary's version, drop the `.tools` upward walk at runtime.
2. No julie `--level` matches code-kb's read set. `full` writes ~60% data code-kb never reads (identifiers, reference_sites, source_regions). `symbols` drops structural_facts and literals that code-kb needs. `symbols` on miller: 416 MB, 9.7 s, 0.8 GB RSS vs 1.3 GB, 21 s, 2.1 GB.
3. code-kb never passes `--parent-pid`, so orphaned scans survive a dead session.
4. Neither product resolves calls now that julie retired resolution for Miller. In the code-kb index 481 of 1,348 internal pending calls are ambiguous by name.
5. julie-extractors carries Miller-only `store` (65k lines), JSONL export, MILLER_* env vars, 362 Miller mentions. Product decision needed.

**IMPACT:** Side effect: miller index rebuilt, now records binary_version 2.42.3 and is stable. Warm reads on miller: outline 0.00 s, refs 0.03 s.
