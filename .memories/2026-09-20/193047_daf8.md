## Plan 020 task 4 fix round 1: exact names through the trigram index, no table scan

Review finding: the exact-name branch in `collect_search_candidates` used `s.name = :query COLLATE NOCASE`, which no index serves, so every search scanned all `symbols` rows (39 ms on the 990k-row hermes-agent index).

**Fix in `crates/code-kb-core/src/queries.rs`:**
- When `symbol_names_tri` exists and the trimmed query has three or more characters, the exact branch is `symbol_names_tri MATCH :exact AND length(s.name) = length(:query)` joined to `symbols` by rowid; `:exact` is the trimmed query in double quotes with inner quotes doubled. A same-length substring is the whole name, case-insensitively.
- Otherwise it falls back to the indexed case-sensitive `s.name = :query`.
- The shared filter fragment now writes `+s.is_test = 0 AND +s.test_container = 0`. Without ANALYZE statistics the planner preferred `idx_symbols_test_container` over `idx_symbols_name_kind` for the fallback (103 ms vs 46 us measured on the hermes-agent copy); the unary plus keeps it on the name index. The word and name branches reach `symbols` by rowid, so the plus changes nothing there.

**Evidence (EXPLAIN QUERY PLAN on read-only backups of the main and hermes-agent indexes):** trigram path = `SCAN symbol_names_tri VIRTUAL TABLE INDEX 0:M1` + `SEARCH s USING INTEGER PRIMARY KEY (rowid=?)`; fallback = `SEARCH s USING INDEX idx_symbols_name_kind (name=?)`; the old NOCASE form = `SCAN s`. Timings on 990k rows: trigram exact 2-9 ms, fallback 46 us, old NOCASE 23-103 ms.

**Tests:** `exact_name_is_admitted_regardless_of_case` also drops the trigram table and checks the case-sensitive fallback; new `exact_name_with_a_quote_is_admitted_through_the_trigram_index` covers the quote doubling; `words_under_three_characters_skip_the_name_branch` already proves the two-character fallback path.
