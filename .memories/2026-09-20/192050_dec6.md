## Plan 020 task 4: three-branch candidate selection for search

`fts_search_symbols_scoped` in `crates/code-kb-core/src/queries.rs` now assembles results from `collect_search_candidates`, which runs three branches with the same WHERE filters and merges them by `rowid` into one `Candidate` per symbol.

- **Word branch** (unchanged rules and ORDER BY): `symbols_fts MATCH and_q`, then `or_q` when every row is documentation. LIMIT is now `word_cap = clamp(limit * 4, 40, 160)` instead of `limit`.
- **Name branch** (new): `symbol_names_tri MATCH "w1" OR "w2" ...` over lowercase query words of three or more characters (stop words dropped unless the whole query is stop words). ORDER BY `bm25(symbol_names_tri) ASC, length(s.name) ASC, s.path ASC` (lead ruling: bm25 on the OR query ranks rows that hit more query words first, so `sidecar_helper_NNN` rows cannot crowd out `parseSha256Sidecar`). LIMIT `name_cap = clamp(limit * 2, 20, 40)`. Skipped when no word qualifies or the table is absent (older index).
- **Exact-name branch** (new): `s.name = :query COLLATE NOCASE`, ORDER BY path then start line, LIMIT `MAX_RESULT_LIMIT`.
- **Interim order** (task 5 replaces it with the rerank): stable sort by tier (code, then documentation, then import) and then branch (exact name, word, name-only); truncate to `limit`. The tier key exists because `documentation_rows_rank_after_code_in_search` asserts a doc heading that equals the query stays behind the code row; `Candidate` carries a `documentation` flag computed in SQL from language and `content_type`.
- `STOP_WORDS` hoisted to module level with `is_stop_word` and `query_words`, shared by the sanitizer and the trigram terms.

**Why:** a symbol only a name substring can reach (`sha256` -> `parseSha256Sidecar`) was never a candidate, and a flood of word matches pushed name matches past the limit (plan 020 design 3, Codex finding 1).
