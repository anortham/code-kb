## Codex review of the search ranking change: 2 code defects fixed, held-out set added

### WHAT
- Codex structured review (validated) of the queries.rs change found: (1) stop-word filtering dropped the unsplit identifier (`isReady` -> only `Ready`*, symbol `before` -> empty query); (2) unsplit alternative ORed against the whole conjunction (`fooBar quux` matched rows with only fooBar and blocked the doc fallthrough); (3) tuning set cannot support a general "beats julie/miller" claim.
- Fixes in `crates/code-kb-core/src/queries.rs`: `sanitize_fts5_query` rewritten: per-identifier groups `(("foo"* "Bar"*) OR "fooBar"*) AND "quux"*` (explicit AND between groups, FTS5 rejects implicit AND after a group); unsplit form kept whenever an identifier split into >1 parts; a query of only stop words is searched as typed; whole-query concatenation only for 2-3 word queries. New `fts5_term` and `name_prefix_query`; `find_related_tests` now uses `name_prefix_query` (name as typed, no split) so `isReady` does not match `test_ready`. Tests added for isReady, before, related-tests strictness.
- Held-out set of 10 queries (incl. 4 against the JS launcher) written after the fix and run once across all three providers.

### Results
- Tuning (16): code-kb file@1 15, sym@1 11, MRR 0.95/0.76; julie lexical 9/3; miller lexical 10/8.
- Held-out (10): code-kb 7/6 (file MRR 0.80); julie lexical 7/2; miller lexical 10/9 (MRR 1.00/0.95).
- Honest claim: code-kb beats julie lexical on both sets and is 4-9x faster; miller still wins held-out because it splits camelCase names at index time (`parseSha256Sidecar` is one FTS5 token; a 4-word query is never concatenated).

- Harness script stays in the session scratchpad on purpose (indexing it contaminates results).
