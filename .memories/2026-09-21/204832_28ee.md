## v1.4.0 benchmark rerun: search quality unchanged, two latency regressions found and fixed on `fix/lookup-latency`

**WHAT:** Reran the six search eval sets (`~/.code-kb/search-eval`) and `scripts/benchmark_quality.py` on the released v1.3.0, v1.3.1, and v1.4.0 binaries (verified from GitHub archives, kept as `bin/code-kb-1.3.0`, `-1.3.1`, `-1.4.0`).

**Search quality:** 0 rank differences between v1.3.0 and v1.4.0 on identical indexes (166 cases). The runner's `--baseline` flags against the morning v1.3.0 files are corpus drift: the code-kb repo merged v1.3.x/v1.4.0 after those runs, and `word_weights`, `weighted_coverage`, `rerank`, `name_tier_score` labels no longer exist (`kb-d2-word-rarity`, `kb-acc2-rerank` are stale labels).

**Performance regressions (MCP session p50, code-kb repo):**
- `lookup_symbol` 2.4 ms -> 10.5 ms, introduced in v1.3.1 (f35c1d3). Cause: `AND (name = :query OR (is_test = 0 ...))` made SQLite plan a MULTI-INDEX OR that runs the test-path predicate over every non-test row. Fix: `+name = :query` (disables index use on that term). SQL timing 9.6 -> 1.2 ms.
- `file_skeleton` 6.2 -> 10.6 ms and +0.7 ms on every read tool, introduced in v1.4.0 (9ce8745 telemetry baseline). Causes: a second `load_file_symbols` only to count rows; `open_read_only` per call in `handle_call_tool` for the tokens-saved SUM. Fix: `count_file_symbols` COUNT query; the dispatcher sums `baseline_bytes` on its open connection.

**After the fix (two rounds):** lookup 2.4 ms, file_skeleton 6.4-6.8 ms, fresh CLI median 15 ms, reconcile 13-15 ms, memory unchanged (post-workload RSS ~35 MB). Guard test: `lookup_statement_is_not_planned_as_a_multi_index_or`. Full workspace tests green, clippy clean. Eval ranks unchanged with the fixed build.

**IMPACT:** Branch `fix/lookup-latency` on top of main (ef170ae), uncommitted, ready for a v1.4.1 patch release once the owner approves.
