## Base-type (extends) edges resolve to the base, never to themselves

Plan 025 wave 2, item 1 (G4 / B2 second half) on `feat/v1.5-qt`.

- **Problem:** the next `julie-extract` emits one `extends` pending row per QML component. A file named like its base (`clock/BarWidget.qml` extending `BarWidget`) resolved to itself, because the "closer candidate" rule in `pending_target_predicate` counted the row's own `from_symbol` as a nearer competitor.
- **Fix (2 lines of SQL, language-agnostic):** an `extends` row never resolves to its own `from_symbol`, and the closer-candidate subquery skips the `from_symbol` for `extends` rows. Every other kind keeps self-resolution, so recursive calls still work.
- **Proved, not changed:** the pending branch of `find_references_internal` already returns `kind: "extends"`, and the impact walk in `compute_blast_radius_scoped` does not filter `p.kind`, so it follows `extends` like `instantiates`. Tests cover both.
- **Tests:** `resolution_test.rs` scans a QML fixture (`Ui/BarWidget.qml`, `clock/BarWidget.qml`, `media/Plugin.qml`), then inserts the synthetic `extends` rows the next extractor will emit. `refs BarWidget --file Ui/BarWidget.qml` lists both derived classes; `refs` on the derived file never lists itself; `blast-radius --file Ui/BarWidget.qml` lists both.
- **Impact:** "which components extend X" is answerable once the extractor ships the rows.
