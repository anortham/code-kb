## Task 3 (plan 021): match strength in the rerank tie-break

**WHAT** — `name_hits` in `crates/code-kb-core/src/queries.rs` now returns a strength per
query word (`u8`) instead of a boolean: 3 for a token run equal to the word, 2 for an equal
stem, 1 for a substring of the collapsed name, 0 for no match. `Hits.name` carries those
strengths, `rerank` gained one sort key (the strength sum, descending) between `score` and
the BM25 keys, and `SearchExplain` gained `name_strength: u32`, printed by `explain_line` in
`formatters.rs` beside the tier as `name <tier>(<sum>)`.

**WHY** — Two candidates with the same score could only be separated by BM25, so a name that
merely contains a short query word as a substring beat a name whose whole token equals it.

**HOW** — The non-zero set of the strengths equals the old boolean, so `weighted_coverage`,
the tier decision and `word_weights` behave exactly as before and no candidate score moved.
`weighted_coverage` now takes an iterator of booleans so the name slice can be mapped without
an allocation. Two red tests proved the old sort picked the substring name when its BM25 was
better; both pass now.

**IMPACT** — One case moved from rank 2 to rank 1 and one from symbol rank 8 to 6 on the
development set; nothing anywhere ranked worse. Development: file@1 69 -> 70, sym@1 60 -> 61,
fileMRR 0.86 -> 0.87. Development-2 and the regression set are unchanged. Warm search p50
stayed at 19 ms.
