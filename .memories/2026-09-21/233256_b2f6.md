## An alias of a Qt module stays outside the workspace

`pending_target_predicate` in `crates/code-kb-core/src/queries.rs` accepted a pending row whenever `p.target_receiver` matched the `alias` or `local_name` of any `import` symbol in the same file. On Kirigami, `import QtQuick.Controls as QQC2` plus `QQC2.Page` made ImagePage.qml look like a caller of Kirigami's own `Page.qml`.

- **Fix:** the alias clause adds `AND COALESCE(json_extract(alias_import.metadata_json, '$.source'), '') NOT LIKE 'Qt%'`. Qt reserves that module prefix, so no workspace module carries it.
- **Test:** `an_alias_of_a_qt_module_does_not_resolve_to_a_workspace_component` in `crates/code-kb-core/tests/resolution_test.rs`. The fixture holds a local `Page.qml`, a `QQC2.Page` site, and a `Kirigami.Page` site. Only the Kirigami site is a caller.
- **Live:** Kirigami `refs Page --file src/controls/Page.qml` prints 3 `extends` rows (TestPage.qml, Page1Form.ui.qml, ScrollablePage.qml) and no ImagePage.qml row. `refs Action --file src/controls/Action.qml` drops 15 sites that name Qt through `QQC2` or `T`; the `Kirigami.Action` sites in the same files stay.
- **Impact:** QML reference lists no longer claim a Qt type as a workspace type.
